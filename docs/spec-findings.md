Implementation findings to feed back into the Magicians threads (WS6). One entry per finding. When the reference implementation and the spec text disagree, we implement the spec and log it here.

## Findings

| Date | ERC | Finding | Status |
|---|---|---|---|
| 2026-09-11 | 8325–8330 | No reference implementation under `ethereum/ERCs/assets/` at the pinned commit; ERC-8320 ships one. Differential tests for 8325–8330 depend on Kula's separate repo (ADR-003). | Noted |
| 2026-09-12 | 8330 | `latestNAVStatus` MUST revert both when a threshold is unconfigured and when no current snapshot exists, with no distinguishing error defined. A consumer cannot tell the two apart from the revert; readers call `heartbeat()`/`maxValuationAge()` first (unconfigured → `unknown`) and only then treat a revert as "no current snapshot" (`fail`). Suggest distinct custom errors. | Open |
| 2026-09-12 | 8325 | "Complete Binding Verification" condition 1 says `getAnchor` must return "the expected token, scope, and token ID" but does not define where the expected scope comes from when a token declares both `IAssetBoundToken` and `IAssetBoundTokenId`. Readers take the strictest reading: TOKEN_ID scope with the supplied `tokenId` when `IAssetBoundTokenId` is declared and a `tokenId` is given, otherwise CONTRACT scope with `boundTokenId == 0`. | Open |
| 2026-09-12 | 8326, 8328, 8330 | None of the three defines how a consumer discovers the anchor / log / oracle contract for a token (no token-side getter, no registry). `subjectId` is opaque. Readers require the address out of band (`--document-anchor`, `--event-log`, `--nav-oracle`) and otherwise report `unsupported`; the same applies to the stream keys `role` and `currency`, which are never guessed. | Open |
| 2026-09-12 | 8320 | Prose says `assetId = keccak256(chainId, contract, subAssetId)` while `getAssetId(contractAddr, subAssetId, chainId)` lists the arguments in another order and the encoding (`abi.encode` vs `abi.encodePacked`) is unstated. Readers never compute `assetId` locally; they always call `getAssetId` on the registry. Two registries could disagree if they encode differently. | Open |
| 2026-09-12 | 8326 | `PROFILE_JSON_RFC8785` requires rejecting "numbers outside the interoperable range" but neither the ERC nor I-JSON (RFC 7493 §2.2, a SHOULD NOT) defines the range or the precision limit. Two conforming canonicalisers can therefore accept and reject different documents (e.g. `9007199254740993`, `0.10000000000000001`, `333333333.33333329` from RFC 8785's own sample). We implement the strictest crisp reading: a literal is accepted only if its ECMAScript `Number::toString` serialisation denotes the same decimal value (rejects overflow, underflow, NaN/Infinity spellings, and any precision loss). Suggest the ERC state the rule. | Open |
| 2026-09-12 | 8326 | `PROFILE_JSON_RFC8785` does not say whether a leading UTF-8 byte order mark is stripped or rejected (RFC 8259 §8.1 lets parsers ignore it). A stripped BOM changes nothing in the output; a rejected one fails the document. We reject, matching the vectors' "no implicit byte-order mark". Suggest the ERC state it. | Open |
| 2026-09-12 | 8326 | `PROFILE_XML_C14N11` says "external entity resolution MUST be disabled" but is silent on internal DTD subsets. Internal entity declarations, `ATTLIST` defaults and attribute-type normalisation all change the Canonical XML output (W3C C14N 1.1 §3.3–3.5), so DTD-aware and DTD-unaware implementations produce different `contentHash` values for the same input. We reject every `DOCTYPE`. Suggest the ERC mandate rejecting any document type declaration, or require full internal-subset processing. | Open |
| 2026-09-12 | 8328 | `recordEvent` takes 13 parameters. With `returns (uint256)` that is more than solc's legacy code generator can keep within stack reach, so a straightforward implementation fails with "stack too deep" and needs `via_ir` (or, as our test fixture does, an unnamed-parameter function that re-decodes calldata). Worth a note in the ERC, since the signature is normative. | Open |
| 2026-09-12 | 8320 | `ClaimProposed` carries only `(assetId, claimType, version, author)`; `validFrom`, `validUntil`, `contentHash` and `uri` are not in any event, so an indexer must `eth_call` `getClaim` per proposal although "Discovery" says the events are the discovery layer. Suggest emitting the window and content hash. | Open |
| 2026-09-12 | 8326, 8330 | `BundleAnchored` omits `anchoredBy` and `metadataURI`; `NAVPublished` omits `methodologyURI`. An indexer recovers `anchoredBy` only as the transaction sender (wrong for contract callers) and cannot recover the URIs without a call. Suggest adding them to the events or stating that they are call-only. | Open |
| 2026-09-13 | 3643 | Live T-REX 1.x tokens (e.g. TREXDINO `0xa4cba3…911e`, `version()` = "1.2") predate the `IIdentityRegistryStorage` split: `identityRegistry().identityStorage()` reverts while `issuersRegistry()` / `topicsRegistry()` answer. The spec text has no version marker, so a reader cannot tell "old release" from "missing function". `erc3643.registryWiring` reports `unsupported` with the failing getter in evidence. | Noted |
| 2026-09-13 | 3643 | T-REX 1.x `ITrustedIssuersRegistry.getTrustedIssuers()` returns `uint[]` issuer indexes (`getTrustedIssuer(uint)` resolves them), not `IClaimIssuer[]`. `uint256[]` and `address[]` share an ABI encoding, so decoding against the spec ABI silently yields `[0x…0001]`; only the following `getTrustedIssuerClaimTopics(address)` reverts. `erc3643.trustedIssuers` reports `unsupported` there; readers should not trust a decoded issuer list whose entries look like small integers. | Noted |
| 2026-09-13 | 3643 | T-REX 1.x compliance contracts implement neither `isTokenBound(address)` nor `getTokenBound()`, and 1.x tokens implement neither `isFrozen(address)` nor `getFrozenTokens(address)` (partial freezing arrived later). `erc3643.complianceBound` and `erc3643.holder` report `unsupported` on such tokens (the holder check names the reverting function). Tokens at `version()` "3.2.0" (Ecowatt, MetalStream, Tokeny TOK) answer every getter in the spec. | Noted |
